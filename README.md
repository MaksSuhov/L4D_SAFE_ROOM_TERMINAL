# Left 4 Dead Interactive Safe-Room Terminal

MVP-сервис на FastAPI: интерактивный терминал безопасной комнаты из Left 4 Dead. Вы выбираете выжившего
(Эллис, Ник, Рошель, Тренер, Билл, Фрэнсис, Луис, Зои), задаёте вопрос, а сервис отвечает **в образе
персонажа**, опираясь на архив лора в Qdrant (RAG: retrieval-augmented generation). Поиск гибридный:
каждая запись несёт косинусный эмбеддинг и разреженный вектор BM25 того же текста, вопрос ищется сразу
по обоим плечам, а их выдачи сливаются по рангам — семантика ловит пересказ, лексика ловит редкое слово.

Архив — это корпус из **русской ветки Left 4 Dead Fandom Wiki** (`left4dead.fandom.com/ru`):
биографии выживших, заражённые с их мутациями и тактикой, кампании, оружие и предметы, режимы и
достижения, «Надписи в убежищах» (граффити со стен) и реплики всех восьми выживших. Корпус читается
на том же языке, на котором терминал отвечает, поэтому поиск моноязычный — это заметно поднимает
сходство и избавляет от провалов кросс-язычного поиска. Каждый чанк помечен уровнем достоверности,
и поиск идёт **двухуровнево**: проверенный лор и слухи со стен ищутся независимо друг от друга,
поэтому надпись на стене никогда не выдаётся за факт, а персонаж пересказывает её так, как ему
свойственно — Ник язвит, Эллис принимает за чистую монету. Перед поиском вопрос разворачивается в
гипотетические формулировки (**HIDE**): игрок спрашивает про персонажа, а нужная запись лежит в
статье про кампанию, где этот персонаж появляется, — такую связь один вектор вопроса не переходит.

Репозиторий — монорепозиторий из двух приложений: бэкенд живёт в корне (`app/`, Python), интерфейс —
в `frontend/` (Vue 3 + Vite + Tailwind CSS). Связь — только по HTTP, через `GET /api/v1/characters`
и `POST /api/v1/chat`; бэкенд разрешает кросс-доменные запросы с dev-сервера фронтенда через CORS.

Проект собран как демонстрация слоистой архитектуры: чистое разделение ответственности, SOLID,
инверсия зависимостей через `Protocol`, полная асинхронность и type hinting.

## Стек

| Слой | Технологии |
|---|---|
| API | FastAPI, Pydantic v2, Uvicorn |
| Бизнес-логика | чистый Python (`services/`), DI через конструкторы |
| Доменные сущности | датаклассы (`domain/`): без ORM, без SQL и без SDK хранилища |
| Векторное хранилище | Qdrant (`qdrant-client`), гибридный поиск: плотный вектор (косинус) + разреженный BM25, слияние рангов через `prefetch` |
| Гибрид | `fastembed` (`Qdrant/bm25`, стеммер и стоп-слова для русского), IDF считает сервер (`Modifier.IDF`) |
| Корпус | Русская ветка Left 4 Dead Fandom Wiki: MediaWiki API + собственные парсеры вики-разметки (`app/ingestion/`) |
| Внешний AI | OpenAI SDK как адаптер к любому OpenAI-совместимому провайдеру: `RouterAI` + Qwen (`qwen/qwen3.7-flash`), OpenAI напрямую или локальный шлюз |
| Наблюдаемость | Langfuse (опционально): один трейс на ход чата, внутри — поиск, расширение HIDE и вызовы модели |
| Интерфейс | Vue 3 (Composition API, `<script setup>`), Vite, Tailwind CSS 4, lucide-vue-next |

### Направление зависимостей

```
routers  ->  services  ->  interfaces (Protocol)  <-  vector / services/ai_service
                    |
             schemas / domain / taxonomy
```

* Пакеты `domain/`, `schemas/` и `services/` держат по модулю на агрегат (или ответственность) и
  реэкспортируют публичные имена через `__init__.py` — импорты остаются стабильными
  (`from app.services import RAGService`), а файлы маленькими.
* `taxonomy.py` держит словарь предметной области (`SourceType`, `LoreTopic`). Он вынесен отдельно,
  потому что им пользуются и хранилище, и схемы, и ингестинг: если бы словарь жил в одном из них,
  остальные зависели бы друг от друга ради двух перечислений.
* `services/rag_service.py`, `services/query_expander.py`, `services/lore_ingestion_service.py` и
  `services/prompt_builder.py` не импортируют ни `qdrant-client`, ни OpenAI, ни `httpx` — только порты
  из `interfaces.py`.
* `ingestion/` — адаптер к чужому сайту: он знает про MediaWiki и вики-разметку, но ничего не знает
  про эмбеддинги, векторы и HTTP-контракт. Это позволяет разбирать вики без базы и без ключа.
* `vector/lore_repository.py` и `vector/character_repository.py` — единственное место, где строится
  язык запросов Qdrant: фильтры, векторы и payload не покидают этих двух файлов.
* `services/ai_service.py` — единственное место, где используется SDK OpenAI.
* `evaluation/` — отдельный пакет оценки: он зависит только от портов (`ClockProtocol`,
  `CompletionProtocol`, `ContextBuilderProtocol`), поэтому прогон датасета проверяется тестами без
  хранилища, без сети и без ключа.
* `routers.py` содержит только маршрутизацию, валидацию (через схемы) и ничего больше.
* Никакого глобального состояния: клиент хранилища и AI-клиент живут в `app.state`, создаются в
  `lifespan` и раздаются через `Depends`.

### Принципы SOLID в коде

* **S** — каждый класс отвечает за одно: `LoreChunkRepository` только хранит и ищет чанки,
  `RAGService` только оркестрирует пайплайн, `OpenAIClient` только говорит с провайдером,
  `GraffitiParser` только разбирает страницу граффити.
* **O** — новый тип внешнего сервиса (например, локальная модель) добавляется классом-адаптером,
  реализующим `AIClientProtocol`; новый источник лора — строкой в `WIKI_SOURCES`; новая разметка
  страницы — парсером, реализующим `CorpusParser`. Существующий код не меняется.
* **L** — конкретные адаптеры реализуют порты целиком и не сужают контракт:
  `QdrantLoreChunkRepository` принимает те же аргументы поиска, что объявляет
  `LoreChunkRepositoryProtocol`, включая текст вопроса для лексического плеча.
* **I** — порты разделены: сервису чата не нужен метод создания чанков, ингестору — метод поиска;
  разрушительный `delete_all()` вообще не попал в сервисный порт, а объявлен отдельным портом
  `LoreArchiveAdminProtocol` — им пользуется только `seed.py`, владелец жизненного цикла архива.
* **D** — `RAGService.__init__` принимает абстракции, а не `QdrantCharacterRepository(client)` и не
  `AsyncOpenAI`.
* **D на практике** — пакет `evaluation/` собран из узких портов: судье нужно только «умение получить
  текстовый ответ», замеру времени — часы, прогону — сборщик контекста. Поэтому весь пайплайн оценки,
  включая замер времени до первого токена, тестируется на заглушках.

## Быстрый старт

### Одной командой

```bash
make dev
```

Цель поднимает весь проект: Qdrant в Docker, архив лора из снимка корпуса (`seed.py`
идемпотентен), бэкенд на `:8000` и фронтенд на `:5173`. Логи обоих процессов идут в один поток с префиксами `backend`/
`frontend`; Ctrl+C останавливает их, контейнер хранилища остаётся поднятым (`make vectors-down` — остановить).

Первый запуск с нуля — две команды: `make install`, затем `cp .env.example .env` и ключ провайдера в
нём; `make dev` создаст `.env` сам, если файла нет.

```bash
make help                      # список всех целей
make vectors                   # поднять Qdrant
make dev-backend               # только API, если хранилище и фронтенд уже подняты
make dev-frontend              # только UI против уже запущенного бэкенда
make seed-reset                # пересоздать коллекции и данные
make reingest                  # переиндексировать архив из снимка корпуса
make import-lore-csv           # перелить архив из выгрузки pgvector без новых эмбеддингов
make corpus-refresh            # перечитать корпус из вики (без хранилища)
make assets                    # пересобрать портреты, фон и знак интерфейса
make check                     # ruff + mypy + pytest
```

Скрипту `scripts/dev.sh` можно передать флаги (`--no-seed`, `--no-vectors`, `--no-frontend`,
`--no-backend`), а порты поменять переменными `BACKEND_PORT` и `FRONTEND_PORT`. Если порт занят —
скрипт останавливается с объяснением, а не падает посреди старта.

Ниже — те же шаги по отдельности, если нужно запустить что-то вручную.

### 1. Зависимости

Нужен Python 3.11+.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt        # рантайм
pip install -r requirements-dev.txt    # + тесты, ruff, mypy, Pillow (ассеты)
```

### 2. Векторное хранилище

```bash
docker compose up -d                   # Qdrant; веб-панель — http://localhost:6333/dashboard
```

Тег образа держится в одной минорной версии с `qdrant-client` из `requirements.txt`: формат сегментов
не читается вперёд, поэтому переход через несколько версий требует переиндексации архива. Гибридному
поиску нужен сервер не старше 1.10 (`prefetch` и слияние рангов).

### 3. Переменные окружения

```bash
cp .env.example .env
# впишите AI_API_KEY и AI_BASE_URL (для RouterAI — ROUTERAI_API_KEY / ROUTERAI_BASE_URL)
```

Провайдер задаётся двумя настройками: `AI_API_KEY` и `AI_BASE_URL`. Любой OpenAI-совместимый
эндпоинт подходит, потому что `OpenAIClient` — это адаптер над OpenAI SDK, а провайдер меняется
только конфигурацией. Поддерживаются три набора имён, первый найденный побеждает:
`AI_*` → `OPENAI_*` → `ROUTERAI_*`.

Важно: **идентификаторы моделей зависят от провайдера**. RouterAI требует вендорный префикс, и
голое имя модель отвергает с `400 Model not found`:

```
# RouterAI / Qwen
EMBEDDING_MODEL=openai/text-embedding-3-small
CHAT_MODEL=qwen/qwen3.7-flash

# OpenAI напрямую (AI_BASE_URL не задан)
EMBEDDING_MODEL=text-embedding-3-small
CHAT_MODEL=gpt-4o-mini
```

Все настройки читаются из окружения (ENV имеет приоритет над `.env`). Основные:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `QDRANT_URL` | `http://localhost:6333` | адрес векторного хранилища |
| `QDRANT_API_KEY` | — | ключ доступа; пусто — локальный узел без аутентификации |
| `LORE_COLLECTION` | `lore_chunks` | коллекция архива: гибридный поиск по уровням доказательств |
| `CHARACTER_COLLECTION` | `characters` | коллекция образов выживших; векторов у неё нет |
| `RAG_HYBRID_ENABLED` | `true` | гибридный поиск; `false` — только косинус |
| `SPARSE_EMBEDDING_MODEL` | `Qdrant/bm25` | модель разреженного вектора; считается локально |
| `SPARSE_EMBEDDING_LANGUAGE` | `russian` | язык BM25: стеммер и стоп-слова должны совпадать с языком корпуса |
| `RAG_PREFETCH_MULTIPLIER` | `4` | во сколько раз шире бюджета каждое плечо набирает кандидатов |
| `AI_API_KEY` | — | ключ провайдера; без него приложение не стартует |
| `AI_BASE_URL` | — | эндпоинт OpenAI-совместимого шлюза; пусто = сам OpenAI |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | модель эмбеддингов (у агрегаторов — с префиксом вендора) |
| `CHAT_MODEL` | `gpt-4o-mini` | модель ответов |
| `RAG_OFFICIAL_TOP_K` | `4` | сколько проверенных записей идёт в контекст |
| `RAG_GRAFFITI_TOP_K` | `3` | сколько надписей со стен идёт в контекст |
| `RAG_VOICE_TOP_K` | `2` | сколько реплик самого персонажа идёт в контекст как образец речи |
| `RAG_MIN_SIMILARITY` | `0.25` | порог косинусного сходства для уровней-доказательств (лор и граффити) |
| `RAG_VOICE_MIN_SIMILARITY` | `0.0` | порог для реплик персонажа: они образец стиля, а не доказательство |
| `HIDE_ENABLED` | `true` | разворачивать вопрос в гипотетические формулировки перед поиском; `false` экономит один запрос к провайдеру |
| `HIDE_MAX_QUESTIONS` | `4` | сколько формулировок расширитель вправе добавить к вопросу |
| `CORPUS_PATH` | `data/corpus/lore.jsonl` | снимок корпуса, который заливается в базу |
| `WIKI_BASE_URL` | `https://left4dead.fandom.com/ru` | вики-источник корпуса: русская ветка, чтобы архив и вопросы были на одном языке |
| `WIKI_CACHE_DIR` | `data/wiki_cache/ru` | кэш сырой вики-разметки; пусто в git, восстанавливается командой |
| `INGESTION_BATCH_SIZE` | `64` | сколько текстов уходит в одном запросе эмбеддингов |
| `CORPUS_LANGUAGE` | `ru` | язык, в который нормализуется корпус при `--translate` |
| `ANSWER_LANGUAGE_INSTRUCTION` | «Всегда отвечай только на русском языке…» | инструкция о языке: дописывается к промпту каждой персоны, поэтому ответы и весь диалог всегда на русском |
| `AUTO_CREATE_COLLECTIONS` | `false` | создать коллекции при старте вместо `seed.py` |
| `API_PREFIX` | `/api/v1` | префикс роутов; пустое значение отдаёт `/characters` и `/chat` |
| `CORS_ALLOW_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | список origin'ов через запятую, которым браузер разрешает звать API; по умолчанию — dev-сервер фронтенда |
| `LANGFUSE_PUBLIC_KEY` | — | публичный ключ проекта Langfuse; пара ключей включает трейсинг |
| `LANGFUSE_SECRET_KEY` | — | секретный ключ проекта Langfuse |
| `LANGFUSE_BASE_URL` | `https://cloud.langfuse.com` | адрес Langfuse API; своя инсталляция указывает свой |
| `LANGFUSE_ENABLED` | `true` | `false` — оставить ключи, но работать с выключенным трейсером |

Размерность эмбеддингов (`EMBEDDING_DIMENSIONS`, по умолчанию 1536) должна совпадать с
размерностью выбранной модели: она задаёт размер плотного вектора коллекции, и вектор другой ширины
хранилище отвергнет.

Язык ответов задаётся не в персонах, а в конфигурации: `ANSWER_LANGUAGE_INSTRUCTION`
дописывается к системному промпту каждой персоны, поэтому терминал отвечает по-русски
независимо от языка вопроса и от того, что лежит в коллекции `characters`. Персоны и few-shot
примеры в `seed.py` тоже на русском.

### 4. Наполнение данными

```bash
python seed.py            # коллекции + 8 выживших + корпус из снимка data/corpus/lore.jsonl
python seed.py --reset    # то же, но сначала пересоздать коллекции
python seed.py --reingest # очистить lore_chunks и залить снимок заново
```

Скрипт идемпотентен: персоны обновляются на месте (правка промпта действует со следующего
запуска, без `--reset`), а записи лора дедуплицируются по хэшу текста, поэтому повторный запуск
ничего не дублирует и не платит за эмбеддинги дважды. Если вы **изменили сам корпус**, нужен
`--reingest`: изменённый текст получает новый хэш и добавился бы рядом со старым.

Подробнее про сбор корпуса — в разделе «Корпус и ингестинг».

### 5. Переезд с pgvector (одноразовый шаг)

Если архив уже был наполнен в PostgreSQL с pgvector, платить за те же эмбеддинги второй раз не нужно:
размерность и метрика совпадают, поэтому достаточно перелить готовые векторы, досчитав только BM25.

```bash
# 1. Выгрузить архив из ещё живого контейнера базы (сделать до его удаления)
mkdir -p data/migration
docker exec l4d_terminal_db psql -U l4d -d l4d_terminal -c "\copy (
    SELECT id, content, content_hash, source_type, topic, title,
           character_name, source_url, embedding::text
    FROM lore_chunks ORDER BY id
) TO STDOUT WITH CSV HEADER" > data/migration/lore_chunks.csv

# 2. Залить выгрузку в Qdrant
make import-lore-csv
```

Перенос идемпотентен: идентификатор точки выводится из хэша текста, поэтому повторный прогон
перезаписывает те же записи, а не удваивает архив. Колонка `id` выгрузки при этом не используется —
пользователю API виден идентификатор, выведенный из хэша, а не номер строки старой базы.

Без выгрузки архив восстанавливается и из снимка корпуса (`python seed.py`), но это второй проход по
всем записям через провайдера, то есть платно.

## Фронтенд

Один экран — «Unified Chat Screen», три зоны: шапка с состоянием канала, лента сообщений и нижний
док с полем ввода и выбором выжившего. Визуально — терминал выживших в убежище: тёмная сталь,
янтарный «голос машины», зелёный для данных из архива, моноширинный шрифт, CRT-оверлей со
scanline'ами. За интерфейсом висит арт из второй части — линейка Особых заражённых, — а в шапке
стоит кровавая «4» из логотипа. Никаких UI-фреймворков поверх Vue: только Tailwind-классы и
немного CSS для эффектов.

### Как устроен код

```
api/            HttpClient (таймаут, AbortController, JSON) -> TerminalApi (доменные вызовы)
composables/    useCharacters (реестр + выбранный), useChat (лента сессии)
components/     TerminalHeader, ChatWindow, ChatMessage, SourceSpoiler,
                ThinkingBubble, ChatComposer, CharacterSelector, CharacterAvatar, EmptyTerminal
```

* **Слой API** — `TerminalApi` знает только два вызова (`listCharacters`, `sendMessage`) и
  собирает URL'ы; компоненты про `fetch`, HTTP-коды и `AbortController` не знают. Сбои транспорта
  приводятся к `ApiError` и к фразе, которую можно показать выжившему (`api/errors.js`).
* **Состояние** — в двух композаблах. `useCharacters` грузит реестр на `onMounted` и держит первого
  выжившего выбранным; `useChat` отвечает за ленту: реплика выжившего добавляется сразу, ответ
  персонажа — по факту ответа, а сбой становится видимой строкой «Сбой канала», а не тихим отказом.
* **Компоненты** — по одной ответственности: `ChatMessage` рисует одно сообщение, `SourceSpoiler`
  сворачивает весь набор источников ответа, `ChatComposer` владеет только вводом. Единственное
  место, где проверяется «можно ли отправить», — `App.vue`, потому что именно он владеет черновиком.

### Что видно на экране

* Вопросы выжившего выравниваются по правому краю, ответы — по левому, с портретом и именем;
  активный персонаж подписан в доке (`Responding agent`, `Ответит: …`).
* Пока идёт ответ, в ленте висит `Thinking`, а поле ввода блокируется и меняет placeholder.
* Источники из RAG занимают под ответом одну тихую строку (`Источники из архива [9]` с разбивкой
  по уровням), которая по клику разворачивается в список записей: **уровень достоверности**
  (официальный лор, граффити на стене, речь персонажа) со своей иконкой и цветом, происхождение
  записи (`No Mercy › The Subway`), косинусное совпадение в процентах и полоска рядом. Каждая
  запись внутри списка сворачивается ещё раз — до своего текста.
  Уровни переводятся в подписи в `lib/lore.js` — граффити намеренно выглядит иначе, чем
  проверенный лор, чтобы слух не читался как факт.
* Селектор выжившего — выпадающий список вверх от кнопки (данные из `GET /api/v1/characters`);
  закрывается по Esc и по клику вне. Смена персонажа не влияет на уже полученные ответы, но
  следующее сообщение уходит с новым `character_id`.
* `Новая сессия` очищает ленту (история живёт в памяти вкладки), `API` ведёт в Swagger,
  статус в шапке отражает доступность реестра и даёт `Переподключиться` при обрыве.

Бэкенд по-прежнему отдаёт только имена — `avatar_url` в схеме персонажа нет, и портреты не
превращаются в данные домена. `CharacterAvatar` берёт картинку из `public/avatars/`, сопоставляя имя
выжившего с файлом в `lib/personas.js`; если файла нет или он не загрузился, остаётся монограмма
с постоянным цветом на имя. Проп `avatarUrl` сохранён как точка расширения, если API когда-нибудь
начнёт присылать свою картинку.

### Ассеты интерфейса

Портреты, фон и логотип не рисуются руками, а нарезаются из файлов вики скриптом
`scripts/fetch_brand_assets.py` (`make assets`), результат коммитится в `frontend/public/` —
как снимок корпуса, чтобы сборка никогда не ходила в сеть:

| Что | Источник | Как получается |
|---|---|---|
| `public/avatars/*.png` | рендеры восьми выживших | из фигуры в полный рост вырезается квадрат по голове: вертикаль считается по bounding box'у фигуры, горизонталь для каждого выжившего задана в таблице (позы разные, правило их не читает) |
| `public/backgrounds/specials.jpg` | обои «Specials» 1920×1200 | обрезается нижняя полоса с водяным знаком фан-сайта |

## Как работает RAG-пайплайн

`RAGService.process_chat_message(character_id, user_message)`:

1. **Персона** — `CharacterRepository.get_by_id()`; если персонажа нет, сразу
   `CharacterNotFoundError` → `404`, без обращения к провайдеру.
2. **Разворачивание вопроса (HIDE)** — `HideQueryExpander.expand(user_message)` просит модель
   разложить вопрос на сущности и связи и вернуть гипотетические формулировки. Последняя из них —
   гипотетический фрагмент статьи. Исходный вопрос всегда идёт первым, поэтому выключенный,
   выпавший или упавший расширитель оставляет поиск точно таким, каким он был без HIDE.
3. **Эмбеддинги всех формулировок** — `OpenAIClient.get_embeddings(...)` одним пакетным запросом:
   расширение стоит одной дополнительной поездки к провайдеру, сколько бы формулировок ни вернулось.
4. **Раздельный поиск по трём уровням.** Вместо одного запроса делаются независимые запросы, у каждого
   свой бюджет и свой порог сходства (`RetrievalPolicy`), а внутри уровня — по одному запросу на
   каждую формулировку:
   * `official` — проверенный лор, `4` записи, порог `0.25`;
   * `graffiti` — надписи со стен, `3` записи, порог `0.25`;
   * `voice` — реплики **самого отвечающего** персонажа (`character_name = character.name`),
     `2` записи, порога нет.

   Это и есть двухуровневость: слухи не конкурируют с фактами за одни и те же слоты контекста,
   поэтому стена граффити не может вытеснить проверенную запись — и наоборот. Формулировки HIDE
   решают лишь, *какие* записи эти слоты займут.
5. **Слияние выдач формулировок** — найденное сливается по хэшу содержимого: запись занимает место в
   бюджете уровня, если её принесла хотя бы одна формулировка, и сохраняет близость той из них, для
   которой она оказалась ближе всего. Одна и та же запись, найденная двумя формулировками, не
   занимает два места; при равной близости выигрывает более ранняя формулировка, а исходный вопрос
   идёт первым, так что гипотеза не может вытеснить прямую находку.
6. **Гибридный поиск** — `QdrantLoreChunkRepository.search_similar_chunks(...)` спрашивает оба плеча
   одним запросом: `prefetch` берёт шире бюджета кандидатов от плотного вектора (косинус) и от
   разреженного BM25, а слияние рангов (`Fusion.RRF`) сводит их в один список. Бюджет уровня
   заполняется **в порядке слияния**, поэтому запись, которую лексическое плечо поставило первой,
   вытесняет ту, которую плотное лишь поставило второй; `similarity` при каждой находке пересчитывается
   по её плотному вектору и остаётся косинусной близостью, чтобы пороги уровней сохранили смысл. Фильтр
   `source_type`/`character_name` прикладывается к обоим плечам сразу: гибрид расширяет воронку внутри
   уровня доказательств, а не поверх его границы.
7. **Порог сходства — свой у каждого уровня.** Для доказательств слабое совпадение это шум, поэтому
   порог отсекает всё ниже `0.25` (эмбеддинги `text-embedding-3-small` на несовместимых текстах
   редко поднимаются выше `0.2`). Порог проверяется для каждой формулировки отдельно — запись
   проходит, если за неё заступилась хотя бы одна. Для реплик персонажа порога нет: это образец речи,
   уже суженный до одного говорящего, и две самые близкие его реплики полезны, даже если вопрос не
   про то, для чего они были записаны.
8. **Сборка брифинга** — `ArchivePromptBuilder` рендерит найденное тремя блоками с разными
   инструкциями: `<official_lore>` (только отсюда можно утверждать факт), `<wall_graffiti>`
   (чужой слух, пересказывать вслух как надпись на стене и относиться сообразно характеру) и
   `<speech_samples>` (копировать манеру речи, но не пересказывать реплики как события). Пустой
   уровень отмечается явно, чтобы модель видела: сведений нет, а не «забыли передать».
9. **Генерация** — системный промпт персоны + инструкция о языке из настроек + брифинг +
   few-shot примеры из `characters.few_shot_examples`. Ответ упаковывается в `ChatResponse` вместе
   с источниками всех трёх уровней.

Роли уровня и характера разведены намеренно: **что можно утверждать** решает пайплайн, а **как это
звучит** решает персона. Ник и Эллис получают одни и те же записи, но первый называет надпись
«чужой графоманией», а второй пересказывает её как свежую новость и вспоминает Кита.

### HIDE: гипотетические формулировки

Один вектор вопроса не переходит от сущности к сущности, и в этом дыра обычного векторного поиска.
Вопрос «какое оружие есть в кампании с Джимми Гиббсом-младшим?» и статья «Вымерший центр › Атриум»
не делят ни одного слова: в вопросе персонаж, в статье — карта и её арсенал. Косинусное сходство
между ними остаётся на уровне шума, и порог `RAG_MIN_SIMILARITY` отсекает единственную запись,
которая отвечает на вопрос.

HIDE (`app/services/query_expander.py`, `HideQueryExpander`) просит модель разложить вопрос на
сущности и связи, назвать их так, как они названы в вики, и дописать один гипотетический фрагмент
статьи. Для того же вопроса модель возвращает «Джимми Гиббс-младший — машина из какой кампании?»,
«Оружие в кампании «Вымерший центр»», «Что можно найти в «Атриуме»?» и фрагмент «Джимми
Гиббс-младший стоит в «Атриуме» — это последняя карта кампании «Вымерший центр», где выжившие
находят дробовик, автомат и штурмовую винтовку». Каждая формулировка ищется своим вектором, поэтому
мост «персонаж → кампания → карта → оружие» проходится по шагам, а не одним прыжком.

* **Исходный вопрос неприкосновенен.** Расширитель только добавляет формулировки. Отказ провайдера
  или неразобранный ответ — не ошибка ответа, а возврат к вопросу игрока: в лог уходит `warning`,
  поиск идёт как без HIDE.
* **Бюджеты и пороги не переписываются.** HIDE меняет, *какие* записи займут места в бюджете уровня,
  а не сколько их: `RAG_OFFICIAL_TOP_K` остаётся бюджетом, а порог проверяется по каждой формулировке
  отдельно.
* **Гипотеза может быть неверной, и HIDE это не лечит.** Расширение покупает перекрытие слов, а не
  истину: на живом прогоне модель иногда называла кампанией «Переход» вместо «Вымершего центра».
  Противовес встроен в конвейер, а не в промпт: исходный вопрос всегда входит в набор формулировок,
  его находки сохраняют свою близость, и бюджет уровня остаётся тем же — неверная гипотеза может
  занять место, но не вытеснить весь уровень.
* **Цена — один запрос к провайдеру перед поиском**, плюс один пакетный запрос на эмбеддинги.
  Вопрос короче трёх слов не разворачивается вовсе: в «привет» нечего раскладывать на сущности.
  Когда важнее время до первого токена, HIDE выключается: `HIDE_ENABLED=false`, и терминал
  возвращается к поиску ровно по вопросу.

Замер на том же вопросе (корпус из 2548 записей, `qwen/qwen3.7-flash`): исходный вопрос находит
запись «Необычные заражённые › Виды необычных заражённых › Джимми Гиббс-младший» с близостью
`0.64` — в ней и лежит мост («его пустую оболочку можно встретить рядом с его же автомобилем в
атриуме вымершего торгового центра»), — но до записей про арсенал она не доходит. Гипотетические
формулировки доводят до них: «Что находят выжившие на картах?» поднимает «Бензопила › Места
появления», а гипотетический фрагмент — «Пистолет «Магнум» › Местонахождение» и «Финал › Left 4
Dead 2 › «Вымерший центр»». Это и есть работа HIDE: не новый ответ, а другой набор записей в тех же
четырёх слотах официального уровня.

## Корпус и ингестинг

Источник лора — русская ветка [Left 4 Dead Fandom Wiki](https://left4dead.fandom.com/ru).
`app/ingestion/` — это адаптер к вики: он скачивает разметку, разбирает её в плоские размеченные
записи и складывает снимок в `data/corpus/lore.jsonl`. Снимок лежит в git, поэтому `seed.py`
воспроизводим, ревьюится в диффе и работает без сети.

Выбор русской ветки — не косметика. Корпус читается на том же языке, на котором терминал отвечает,
поэтому поиск моноязычный, а не кросс-язычный: замер на этом корпусе — запрос «зомби клоуны»
получает `0.38` к разделу «Клоун» и `0.51` к «Мрачному карнавалу», тогда как по английскому корпусу
те же чанки давали `0.24–0.26` и проваливались под порог `RAG_MIN_SIMILARITY`. Расплата — русская
вика примерно вдвое компактнее английской, зато она же закрывает разделы, которых в английском
корпусе не было вовсе: оружие, предметы, локации, режимы, достижения.

объявить редирект означало бы и скачать страницу дважды, и подписать её текстом чужого имени.

### Как разбираем

* **`wikitext.py`** чистит MediaWiki-разметку: сноски, галереи, атрибуты, ссылки, таблицы. Две
  вещи сохранены осознанно. **Инфобоксы** (`{{Infobox infected|Health = 4000 …}}`) превращаются в
  строки `Health — 4000 (Normal & Survival)`: характеристики заражённых — самый спрашиваемый факт
  в архиве, и выбрасывать шаблоны целиком означало бы выбрасывать ровно их. **Таблицы** не
  удаляются, а выравниваются в строки, по той же причине. Отдельно закрыты три ловушки русской
  разметки: локализованные пространства имён (`[[Файл:…]]`), ссылка внутри подписи к файлу и
  опечатки самой вики, оставляющие висячие `]]`.
* **`GraffitiParser`** читает таблицу «оригинал — перевод», которой русская вика заменила списки:
  строка таблицы — это надпись на английском и её русский перевод, а `colspan`-заголовок называет
  место. В запись идёт русская колонка, заголовок — `кампания › место` (`Нет милосердию › Метро`).
  Пунктирный формат английской вики тоже поддерживается — им написаны прозаические примечания на
  той же странице.
* **`ArticleParser`** режет статью по заголовкам и абзацам (потолок ~900 символов, чтобы в промпт
  влезало несколько записей). Лид статьи сохраняется всегда: это её собственное резюме. Заголовок
  записи — путь до раздела (`Танк › Механика › Атаки`).
* **`SubtitlesParser`** собирает голосовой профиль из субтитров: русская вика хранит реплики
  таблицей «русский — английский» с техническим именем блока вместо ситуации, поэтому парсер берёт
  русскую колонку, отбрасывает английскую по маркеру `[english]`, снимает префикс говорящего
  («Эллис: »), убирает односложные реакции и повторы. Потолка на персонажа здесь нет: фильтры уже
  выбросили всё, что не составляет манеру речи, а обрезка отрезала бы только поздние главы.
* **`QuotesParser`** остаётся для пунктирного формата английской вики — на случай, если реестр
  когда-нибудь снова посмотрят на неё.

### Команды

```bash
make corpus-refresh    # перечитать вики и пересобрать снимок (без базы)
make reingest          # очистить lore_chunks и залить снимок заново
make seed              # схема + персоны + инкрементальный ингестинг снимка
python seed.py --refresh --corpus-only            # то же, что corpus-refresh
python seed.py --refresh --corpus-only --translate # + нормализация языка корпуса
```

Разметка кэшируется в `data/wiki_cache/ru/` (в git не попадает), поэтому разбор можно повторять без
сети, а `--refresh` принудительно перечитывает страницы. Кэш имён файлов переживает кириллицу:
слаг строится по `\w` с флагом Unicode, иначе все русские заголовки схлопнулись бы в один файл.

### Про перевод корпуса

`translation.py` остаётся в пайплайне, но теперь он не нужен: корпус уже читается по-русски, и
`CORPUS_LANGUAGE=ru` совпадает с языком исходника, так что `--translate` ничего не изменит. Этап
полезен, если источником снова станет английская вика: замер на английском корпусе показывал
`0.53` у русского вопроса против английской записи и `0.74` против её русского перевода. Перевод —
дорогой проход (16 коротких строк ≈ 21 с, длинный абзац ≈ 47 с), поэтому он **выключен по
умолчанию**; непереведённый текст сохраняется как есть.

## Оценка качества (LLM-судья)

`app/evaluation/` — отдельный пакет, который прогоняет вопросы через тот же RAG-пайплайн и считает
по каждому ответу оценки судьи, близость к эталону, качество поиска и время ответа.

### Что измеряется

| Метрика | Что означает | Шкала |
|---|---|---|
| Точность (accuracy) | нет ли выдуманных фактов, не противоречит ли ответ эталону и архиву | 1–5 |
| Полнота (completeness) | раскрыты ли ключевые моменты эталона | 1–5 |
| Релевантность (relevance) | отвечает ли ответ именно на заданный вопрос | 1–5 |
| Лексический F1 | пересечение значимых слов ответа и эталона, с отброшенными служебными словами и приведёнными к основе формами | 0–1 |
| Семантическая близость | косинус эмбеддингов ответа и эталона: видит пересказ своими словами | 0–1 |
| Полнота поиска (recall) | какую долю ожидаемых тем нашёл поиск | 0–1 |
| Все темы найдены (full_hit) | доля кейсов, где нашлись **все** ожидаемые темы | 0–1 |
| MRR | обратное место первой найденной темы: 1.0 — тема стоит первой в выдаче | 0–1 |
| Точность поиска (precision) | какая доля найденных заголовков относится к ожидаемым темам; ограничена бюджетом top-k | 0–1 |
| Время до первого токена | сколько проходит от запроса до первого фрагмента ответа | секунды |
| Полное время | сколько идёт генерация целиком | секунды |

Первые три ставит языковая модель по строгому шаблону (`judge.py`): она получает вопрос, архивные
выдержки, эталон и — **последним** — ответ терминала, и обязана вернуть JSON с тремя целыми числами.
Оцениваемый ответ идёт последним и помечен отдельно от справки намеренно: слабая модель склонна
оценивать то, что лежит рядом с вопросом, и когда ответ шёл первым, она нередко оценивала эталон
вместо него. По той же причине пустой ответ судье не отдаётся вовсе — он получает низший балл без
обращения к модели, иначе она выставила бы высокие баллы по одному эталону.

Близость к эталону меряется двумя способами, потому что они ловят разное. Лексический F1
(`metrics.py`) сравнивает значимые слова, приведённые к основе: русский флективный, и без стемминга
«танк», «танка» и «танку» считались бы разными словами, а служебные слова дали бы совпадение на
пустом месте. Семантическая близость (`similarity.py`) считает косинус эмбеддингов и потому видит
пересказ своими словами — а ответы терминала пересказывают эталон в образе персонажа, и по одним
словам они расходятся сильно. Качество поиска (`metrics.py`) считается по заголовкам: `recall` и
`full_hit` отвечают, нашлось ли, `mrr` — на каком месте, а `precision` ограничена бюджетом top-k и
потому не может быть высокой. **Время до первого токена** требует потоковой генерации:
`RAGService.build_chat_context` отдаёт готовый контекст и источники, `OpenAIClient.stream_response`
шлёт ответ по фрагментам, а `latency.measure_stream` засекает момент первого фрагмента и конец.
Обычный `POST /chat` при этом не меняется — он идёт по-прежнему через `generate_response`.

### Сбои и воспроизводимость

Провайдер изредка отвечает потоком без единого фрагмента. Адаптер видит в этом ошибку
(`stream_response` падает, как и буферизованный путь), стенд повторяет кейс, а кейс, не давший ответа
за все попытки, попадает в отчёт **отдельной строкой сбоя**, а не в средние. Иначе пустой ответ
растворился бы в арифметике, и чем хуже шёл прогон, тем лучше выглядели бы средние. Генерация на
стенде идёт при закреплённой температуре (`EVAL_TEMPERATURE`, по умолчанию 0), а не при боевой 0.7:
без этого один и тот же датасет давал бы разные числа от прогона к прогону. Настройки прогона
(модель, температура, число попыток, датасет) пишутся в `report.json` рядом с числами, чтобы отчёт
можно было сравнить с прошлым.

### Как запустить

```bash
make eval
# или напрямую:
python -m scripts.evaluate --dataset data/eval/questions.jsonl --limit 5
```

Нужны поднятая база, наполненный архив и `AI_API_KEY`. Скрипт собирает зависимости через
`get_rag_service`, то есть оценивает ровно тот пайплайн, который отвечает игрокам, а не его копию.
Отчёт печатается в терминал и пишется в `data/eval/report.json`.

### Как устроен пакет

Слои идут сверху вниз, и каждый знает только про соседа снизу:

| Слой | Файл | Ответственность |
|---|---|---|
| Значения | `domain.py` | `EvalCase`, `JudgeScore`, `Overlap`, `SourceOverlap`, `Timing`, `CaseResult`, `CaseFailure` — контейнеры данных |
| Порты | `interfaces.py` | `ClockProtocol`, `CompletionProtocol`, `StreamingChatProtocol`, `EmbeddingProtocol`, `SimilarityProtocol`, `ContextBuilderProtocol`, `JudgeProtocol` |
| Метрики | `metrics.py` | чистые функции `text_overlap`, `source_overlap`, `tokenize`, `stem`, `content_tokens` |
| Близость | `similarity.py` | `EmbeddingSimilarity` (косинус эмбеддингов) и его выключенная заглушка `NullSimilarity` |
| Судья | `judge.py` | `LLMJudge` — промпт и разбор ответа модели |
| Замеры | `latency.py` | `MonotonicClock`, `measure_stream` |
| Датасет | `dataset.py` | `load_cases` — чтение JSONL |
| Оркестрация | `runner.py` | `CaseEvaluator` (один кейс), `EvaluationService` (весь датасет) |
| Отчёт | `report.py` | `EvaluationReport` — средние значения, текст, JSON |

Ни один слой не знает про Qdrant, OpenAI SDK или HTTP: всё общение идёт через порты из
`interfaces.py`. Поэтому прогон целиком проверяется на заглушках (`tests/test_eval_runner.py`) — с
in-memory репозиториями, поддельным стримом и часами, которые можно двигать вручную. Детерминизм
здесь важнее удобства: без управляемых часов нельзя было бы проверить, что время до первого токена
считается именно от запроса до первого фрагмента, а не от запроса до конца ответа.

### Формат датасета

`data/eval/questions.jsonl`, один JSON-объект на строку:

```json
{"question": "Кто такой Танк и как с ним бороться?", "character_id": 5,
 "reference_answer": "Танк — самый крупный особый заражённый...", "expected_sources": ["Танк"],
 "tags": ["infected", "tactics"]}
```

`character_id` — идентификатор из сида: 1 Эллис, 2 Ник, 3 Рошель, 4 Тренер, 5 Билл, 6 Фрэнсис,
7 Луис, 8 Зои. `expected_sources` сравниваются нестрого: тема «Танк» считается найденной, если она
встречается внутри заголовка источника («Танк › Базовые стратегии»). Эталонный ответ и ожидаемые
темы необязательны: без них судья опирается только на архив, а соответствующая метрика не считается.

В поставке 21 кейс — все восемь персонажей, темы от особых заражённых до предметов лечения и механик
(теги `infected`, `items`, `mechanics`, `tactics`, `modes`, `safe_rooms`, `infection`). Этого хватает,
чтобы увидеть разницу между темами, но средние по подгруппам ещё шумят: числа по тегу стоит читать
как ориентир, а не как измерение с точностью до сотых.

## Наблюдаемость (Langfuse)

Трейсинг опционален и включается ключами. Если задана пара ключей, каждый ход чата становится одним
трейсом, внутри которого видны поиск, расширение HIDE и сами вызовы модели — со временем, токенами
и стоимостью. Без ключей собирается выключенный трейсер (`NoOpTracer`), и код идёт тот же самый:
наблюдаемость не ветвит бизнес-логику и ничего не отправляет наружу.

```
LANGFUSE_PUBLIC_KEY=pk-lf-...
LANGFUSE_SECRET_KEY=sk-lf-...
LANGFUSE_BASE_URL=https://cloud.langfuse.com   # EU по умолчанию; для US — us.cloud.langfuse.com
LANGFUSE_ENABLED=true                          # false — оставить ключи, но работать без трейсинга
```

Ключи берутся в проекте Langfuse (`cloud.langfuse.com` или своя инсталляция) — это **не** ключи
провайдера модели. Своя инсталляция Langfuse требует Postgres, ClickHouse, Redis и S3-хранилище:
это отдельный стек, а не сервис в `docker-compose.yml` этого проекта.

### Что видно в трейсе

Один `POST /chat` даёт дерево `chat` → (`hide-expand`, `retrieve`, `generation`). Участок `retrieve`
несёт в метаданных свои формулировки и пары «id записи, близость» по каждому уровню доказательств, а
`chat` — вопрос и готовый ответ. Это и делает retrieval-часть проверяемой: видно не только ответ, но
и на чём он построен.

### Как это устроено

Слой сервисов не импортирует SDK наблюдаемости. `RAGService` и `HideQueryExpander` зависят от порта
`TracerProtocol` (`app/interfaces.py`), реализации живут в `app/services/tracing.py`:

| Тип | Роль |
|---|---|
| `TracerProtocol`, `TracingSpanProtocol` | порт: открыть участок, приложить к нему вход, выход и метаданные |
| `NoOpTracer` | выключенный трейсер: `nullcontext`, разметка отбрасывается |
| `LangfuseTracer` | адаптер над клиентом Langfuse; владеет и его жизненным циклом (`flush`, `shutdown`) |

`build_tracer` собирает трейсер по настройкам один раз в `lifespan` и закрывает там же при остановке.
Наблюдения уходят в Langfuse пачками, поэтому `flush` при остановке — единственный способ не потерять
последние секунды трейсов; по той же причине `scripts/evaluate.py` сбрасывает очередь в конце, иначе
прогон стенда не оставил бы трейсов вовсе.

Сами вызовы модели трассируются не портом, а drop-in адаптером: `app/services/ai_service.py`
импортирует `AsyncOpenAI` из `langfuse.openai`, поэтому поколения и эмбеддинги попадают в трейс
автоматически. `LangfuseTracer` создаёт клиент **явно** из `Settings` — и только такой клиент видит
drop-in, потому что переменные из `.env` в окружение процесса не попадают.

## Тесты

```bash
pytest                                     # всё: юнит-тесты + интеграционные, без хранилища и сети
pytest tests/test_rag_service.py           # только бизнес-логика, без хранилища и сети
pytest tests/test_ingestion_parsers.py     # разбор вики-разметки на встроенных примерах
pytest tests/test_eval_runner.py           # оценка: метрики, судья и прогон на заглушках
```

**Юнит-тесты** не обращаются ни к хранилищу, ни к сети, ни к вики: `tests/fakes.py` содержит
in-memory реализации портов и детерминированный AI-клиент, `tests/test_ingestion_parsers.py`
работает на встроенной вики-разметке, а в `tests/test_api.py` через `dependency_overrides`
подменяются только внешние адаптеры — реальные роутеры, DI-граф и `RAGService` при этом работают
по-настоящему. Это и есть проверка того, что инверсия зависимостей сделана корректно.

Так же проверяется и оценка: `tests/test_eval_metrics.py` считает формулы на строках,
`tests/test_eval_judge.py` разбирает ответы судьи через заглушку модели, а
`tests/test_eval_runner.py` прогоняет реальный `RAGService` на in-memory репозиториях с поддельным
стримом и управляемыми часами — то есть время до первого токена проверяется точно, без ожидания.

**Интеграционные тесты** (`tests/test_integration_qdrant.py`) поднимают всё по-настоящему, но в
процессе: Qdrant работает в локальном режиме (`AsyncQdrantClient(":memory:")`), реальные репозитории
ищут гибридно, `seed.py` наполняет обе коллекции, а провайдер подменяется локальной HTTP-заглушкой
(`tests/provider_server.py`) — ни сети, ни ключа, ни контейнера. Отдельный тест пришпиливает главное
свойство гибрида: запись, которую лексическое плечо поставило первой, попадает в бюджет уровня, хотя
плотное плечо поставило её последней. Локальный Qdrant не применяет payload-индексы, поэтому тест
отключает одно его предупреждение; фильтры при этом работают.

```bash
ruff check .       # линтер
mypy               # статическая типизация (конфиг в pyproject.toml)
```

## Замечания по реализации

* Коллекция архива держит **два именованных вектора одной точки**: плотный (`dense`, косинус) и
  разреженный (`bm25`). Держать их врозь значило бы повторять фильтр уровня в двух запросах и
  склеивать выдачу на клиенте, а `prefetch` делает это на сервере одним обращением.
* `Modifier.IDF` включён на разреженном векторе, поэтому энкодер кладёт в него частоты терминов, а IDF
  считает сервер по статистике коллекции: запись, впервые увиденная на запросе, всё равно получает
  верный вклад, и словарь не нужно хранить и синхронизировать на клиенте.
* Бюджет уровня наполняется в порядке слияния рангов, а `similarity` только **сообщается** как
  косинусная близость. Пересортировка по косинусу до отсечения бюджета обнулила бы гибрид: плотное
  плечо уже отдаёт свой глобальный топ, поэтому верхушка объединения совпала бы с верхушкой одного
  плотного плеча.
* Идентификатор точки выводится из хеша текста, поэтому повторная запись перезаписывает свою точку, а
  не создаёт вторую: наполнение идемпотентно без отдельного учёта уже сохранённого.
* Клиент Qdrant проверяет версию сервера при создании, а это сетевой вызов; настройка
  `QDRANT_CHECK_COMPATIBILITY=false` оставляет сборку графа офлайн, а живость хранилища сообщает
  проба готовности.
* Комментарии в коде только там, где решение неочевидно (например, почему бюджет уровня наполняется
  в порядке слияния, а близость при этом только сообщается).
