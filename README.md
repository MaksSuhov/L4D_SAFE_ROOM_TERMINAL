# Left 4 Dead Interactive Safe-Room Terminal

MVP-сервис на FastAPI: интерактивный терминал безопасной комнаты из Left 4 Dead. Вы выбираете выжившего
(Эллис, Ник, Рошель, Тренер, Билл, Фрэнсис, Луис, Зои), задаёте вопрос, а сервис отвечает **в образе
персонажа**, опираясь на архив лора из PostgreSQL + pgvector (RAG: retrieval-augmented generation).

Архив — это корпус из **Left 4 Dead Fandom Wiki**: биографии выживших, заражённые с их мутациями,
кампании, «Safe Room Inscriptions» (граффити со стен убежищ) и полные дампы реплик всех восьми
выживших. Каждый чанк помечен уровнем достоверности, и поиск идёт **двухуровнево**: проверенный лор
и слухи со стен ищутся независимо друг от друга, поэтому надпись на стене никогда не выдаётся за факт,
а персонаж пересказывает её так, как ему свойственно — Ник язвит, Эллис принимает за чистую монету.

Репозиторий — монорепозиторий из двух приложений: бэкенд живёт в корне (`app/`, Python), интерфейс —
в `frontend/` (Vue 3 + Vite + Tailwind CSS). Связь — только по HTTP, через `GET /api/v1/characters`
и `POST /api/v1/chat`; бэкенд разрешает кросс-доменные запросы с dev-сервера фронтенда через CORS.

Проект собран как демонстрация слоистой архитектуры: чистое разделение ответственности, SOLID,
инверсия зависимостей через `Protocol`, полная асинхронность и type hinting.

## Стек

| Слой | Технологии |
|---|---|
| API | FastAPI, Pydantic v2, Uvicorn |
| Бизнес-логика | чистый Python (`services/`), DI через конструкторы |
| Доступ к данным | SQLAlchemy 2.0 (`Mapped` / `mapped_column`), `AsyncSession`, asyncpg |
| Векторный поиск | PostgreSQL 16 + pgvector (косинусное расстояние, HNSW-индекс) |
| Корпус | Left 4 Dead Fandom Wiki: MediaWiki API + собственные парсеры вики-разметки (`app/ingestion/`) |
| Внешний AI | OpenAI SDK как адаптер к любому OpenAI-совместимому провайдеру: `RouterAI` + Qwen (`qwen/qwen3.7-flash`), OpenAI напрямую или локальный шлюз |
| Интерфейс | Vue 3 (Composition API, `<script setup>`), Vite, Tailwind CSS 4, lucide-vue-next |

### Направление зависимостей

```
routers  ->  services  ->  interfaces (Protocol)  <-  repositories / services/ai_service
                    |
             schemas / models / taxonomy
```

* Пакеты `models/`, `schemas/` и `services/` держат по модулю на агрегат (или ответственность) и
  реэкспортируют публичные имена через `__init__.py` — импорты остаются стабильными
  (`from app.services import RAGService`), а файлы маленькими.
* `taxonomy.py` держит словарь предметной области (`SourceType`, `LoreTopic`). Он вынесен отдельно,
  потому что им пользуются и ORM, и схемы, и ингестинг: если бы словарь жил в одном из них, остальные
  зависели бы друг от друга ради двух перечислений.
* `services/rag_service.py`, `services/lore_ingestion_service.py` и `services/prompt_builder.py` не
  импортируют ни SQLAlchemy, ни OpenAI, ни `httpx` — только порты из `interfaces.py`.
* `ingestion/` — адаптер к чужому сайту: он знает про MediaWiki и вики-разметку, но ничего не знает
  про эмбеддинги, векторы и HTTP-контракт. Это позволяет разбирать вики без базы и без ключа.
* `repositories.py` — единственное место, где строится SQL.
* `services/ai_service.py` — единственное место, где используется SDK OpenAI.
* `routers.py` содержит только маршрутизацию, валидацию (через схемы) и ничего больше.
* Никакого глобального состояния: engine, сессия и AI-клиент живут в `app.state`, создаются в
  `lifespan` и раздаются через `Depends`.

### Принципы SOLID в коде

* **S** — каждый класс отвечает за одно: `LoreChunkRepository` только хранит и ищет чанки,
  `RAGService` только оркестрирует пайплайн, `OpenAIClient` только говорит с провайдером,
  `GraffitiParser` только разбирает страницу граффити.
* **O** — новый тип внешнего сервиса (например, локальная модель) добавляется классом-адаптером,
  реализующим `AIClientProtocol`; новый источник лора — строкой в `WIKI_SOURCES`; новая разметка
  страницы — парсером, реализующим `CorpusParser`. Существующий код не меняется.
* **L** — конкретные репозитории наследуют `BaseRepository[T]` и не сужают его контракт.
* **I** — порты разделены: сервису чата не нужен метод создания чанков, ингестору — метод поиска;
  разрушительный `delete_all()` вообще не попал в порт — им пользуется только `seed.py`, владелец
  жизненного цикла архива.
* **D** — `RAGService.__init__` принимает абстракции, а не `CharacterRepository(session)` и не
  `AsyncOpenAI`.

## Быстрый старт

### Одной командой

```bash
make dev
```

Цель поднимает весь проект: PostgreSQL в Docker, архив лора из снимка корпуса (`seed.py`
идемпотентен), бэкенд на `:8000` и фронтенд на `:5173`. Логи обоих процессов идут в один поток с префиксами `backend`/
`frontend`; Ctrl+C останавливает их, контейнер базы остаётся поднятым (`make db-down` — остановить).

Первый запуск с нуля — две команды: `make install`, затем `cp .env.example .env` и ключ провайдера в
нём; `make dev` создаст `.env` сам, если файла нет.

```bash
make help                      # список всех целей
make dev-backend               # только API, если база и фронтенд уже подняты
make dev-frontend              # только UI против уже запущенного бэкенда
make seed-reset                # пересоздать схему и данные
make reingest                  # переиндексировать архив из снимка корпуса
make corpus-refresh            # перечитать корпус из вики (без базы)
make check                     # ruff + mypy + pytest
```

Скрипту `scripts/dev.sh` можно передать флаги (`--no-seed`, `--no-db`, `--no-frontend`,
`--no-backend`), а порты поменять переменными `BACKEND_PORT` и `FRONTEND_PORT`. Если порт занят —
скрипт останавливается с объяснением, а не падает посреди старта.

Ниже — те же шаги по отдельности, если нужно запустить что-то вручную.

```bash
python3 -m venv .venv
source .venv/bin/activate
```


### 3. Переменные окружения

```bash
cp .env.example .env
# впишите AI_API_KEY и AI_BASE_URL (для RouterAI — ROUTERAI_API_KEY / ROUTERAI_BASE_URL)
```

Провайдер задаётся двумя настройками: `AI_API_KEY` и `AI_BASE_URL`. Любой OpenAI-совместимый
эндпоинт подходит, потому что `OpenAIClient` — это адаптер над OpenAI SDK, а провайдер меняется
только конфигурацией. Поддерживаются три набора имён, первый найденный побеждает:
`AI_*` → `OPENAI_*` → `ROUTERAI_*`.

Важно: **идентификаторы моделей зависят от провайдера**. RouterAI требует вендорный префикс, и
голое имя модель отвергает с `400 Model not found`:

```
# RouterAI / Qwen
EMBEDDING_MODEL=openai/text-embedding-3-small
CHAT_MODEL=qwen/qwen3.7-flash

# OpenAI напрямую (AI_BASE_URL не задан)
EMBEDDING_MODEL=text-embedding-3-small
CHAT_MODEL=gpt-4o-mini
```

Все настройки читаются из окружения (ENV имеет приоритет над `.env`). Основные:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://l4d:l4d@localhost:5432/l4d_terminal` | DSN для asyncpg |
| `AI_API_KEY` | — | ключ провайдера; без него приложение не стартует |
| `AI_BASE_URL` | — | эндпоинт OpenAI-совместимого шлюза; пусто = сам OpenAI |
| `EMBEDDING_MODEL` | `text-embedding-3-small` | модель эмбеддингов (у агрегаторов — с префиксом вендора) |
| `CHAT_MODEL` | `gpt-4o-mini` | модель ответов |
| `RAG_OFFICIAL_TOP_K` | `4` | сколько проверенных записей идёт в контекст |
| `RAG_GRAFFITI_TOP_K` | `3` | сколько надписей со стен идёт в контекст |
| `RAG_VOICE_TOP_K` | `2` | сколько реплик самого персонажа идёт в контекст как образец речи |
| `RAG_MIN_SIMILARITY` | `0.25` | порог косинусного сходства для уровней-доказательств (лор и граффити) |
| `RAG_VOICE_MIN_SIMILARITY` | `0.0` | порог для реплик персонажа: они образец стиля, а не доказательство |
| `CORPUS_PATH` | `data/corpus/lore.jsonl` | снимок корпуса, который заливается в базу |
| `WIKI_BASE_URL` | `https://left4dead.fandom.com` | вики-источник корпуса |
| `WIKI_CACHE_DIR` | `data/wiki_cache` | кэш сырой вики-разметки; пусто в git, восстанавливается командой |
| `INGESTION_BATCH_SIZE` | `64` | сколько текстов уходит в одном запросе эмбеддингов |
| `CORPUS_LANGUAGE` | `ru` | язык, в который нормализуется корпус при `--translate` |
| `ANSWER_LANGUAGE_INSTRUCTION` | «Всегда отвечай только на русском языке…» | инструкция о языке: дописывается к промпту каждой персоны, поэтому ответы и весь диалог всегда на русском |
| `AUTO_CREATE_TABLES` | `false` | создать схему при старте вместо `seed.py` |
| `API_PREFIX` | `/api/v1` | префикс роутов; пустое значение отдаёт `/characters` и `/chat` |
| `CORS_ALLOW_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173` | список origin'ов через запятую, которым браузер разрешает звать API; по умолчанию — dev-сервер фронтенда |

Размерность эмбеддингов (`EMBEDDING_DIMENSIONS`, по умолчанию 1536) должна совпадать с
размерностью выбранной модели: она задаёт тип колонки `Vector(...)` в pgvector.

Язык ответов задаётся не в персонах, а в конфигурации: `ANSWER_LANGUAGE_INSTRUCTION`
дописывается к системному промпту каждой персоны, поэтому терминал отвечает по-русски
независимо от языка вопроса и от того, что лежит в таблице `characters`. Персоны и few-shot
примеры в `seed.py` тоже на русском.

### 4. Наполнение данными

```bash
python seed.py            # схема + 8 выживших + корпус из снимка data/corpus/lore.jsonl
python seed.py --reset    # то же, но сначала удалить таблицы
python seed.py --reingest # очистить lore_chunks и залить снимок заново
```

Скрипт идемпотентен: персоны обновляются на месте (правка промпта действует со следующего
запуска, без `--reset`), а записи лора дедуплицируются по хэшу текста, поэтому повторный запуск
ничего не дублирует и не платит за эмбеддинги дважды. Если вы **изменили сам корпус**, нужен
`--reingest`: изменённый текст получает новый хэш и добавился бы рядом со старым.

Подробнее про сбор корпуса — в разделе «Корпус и ингестинг».

### 5. Запуск

```bash
uvicorn app.main:app --reload
```

* Swagger UI — http://127.0.0.1:8000/docs
* ReDoc — http://127.0.0.1:8000/redoc

## API

### `GET /api/v1/characters`

```bash
curl -s http://127.0.0.1:8000/api/v1/characters
```

```json
[
  {
    "id": 1,
    "name": "Эллис",
    "system_prompt": "Ты — Эллис, жизнерадостный молодой механик из Саванны...",
    "few_shot_examples": [{"user": "...", "assistant": "..."}]
  }
]
```

### `POST /api/v1/chat`

```bash
curl -s -X POST http://127.0.0.1:8000/api/v1/chat \
  -H 'Content-Type: application/json' \
  -d '{"character_id": 1, "message": "Как нам убить Танка?"}'
```

```json
{
  "character_id": 2,
  "character_name": "Ник",
  "answer": "Тут на стенах пишут, что это военный эксперимент, а кто-то дорисовал и инопланетян...",
  "model": "qwen/qwen3.7-flash",
  "sources": [
    {
      "id": 1183,
      "source_type": "official",
      "topic": "infection",
      "title": "Green Flu › Overview",
      "character_name": null,
      "content": "The Green Flu, commonly referred to as the Infection, is the name given to the unknown virus...",
      "similarity": 0.45
    },
    {
      "id": 2401,
      "source_type": "graffiti",
      "topic": "graffiti",
      "title": "Dead Air › The Construction Site",
      "character_name": null,
      "content": "OPEN YOUR EYES\n↳ This virus was a military\n↳ experiment. It was engineered\n↳ in a lab!\n↳ <-- BY ALIENS",
      "similarity": 0.29
    }
  ]
}
```

Поле `sources` возвращает записи, на которых построен ответ, вместе с уровнем достоверности,
происхождением и косинусным сходством — это делает RAG наблюдаемым и упрощает отладку. Для
голосовых записей (`source_type: "voice"`) в `character_name` указан говорящий.

| Код | Когда |
|---|---|
| `200` | ответ сформирован |
| `404` | персонаж с таким `character_id` не найден |
| `422` | `message` пустой, длиннее 2000 символов или `character_id <= 0` |
| `502` | провайдер вернул ошибку или не сконфигурирован ключ |

Браузерные запросы к API разрешены только с origin'ов из `CORS_ALLOW_ORIGINS`: по умолчанию это
dev-сервер фронтенда, поэтому отдельный прокси для разработки не обязателен.

### `GET /api/v1/health`

Проверяет живость процесса и доступность PostgreSQL (`SELECT 1`), возвращая
`{"status": "ok", "version": "0.1.0", "database": "ok"}`.

## Фронтенд

Один экран — «Unified Chat Screen», три зоны: шапка с состоянием канала, лента сообщений и нижний
док с полем ввода и выбором выжившего. Визуально — терминал выживших в убежище: тёмная сталь,
янтарный «голос машины», зелёный для данных из архива, моноширинный шрифт, CRT-оверлей со
scanline'ами. Никаких UI-фреймворков поверх Vue: только Tailwind-классы и немного CSS для эффектов.

### Как устроен код

```
api/            HttpClient (таймаут, AbortController, JSON) -> TerminalApi (доменные вызовы)
composables/    useCharacters (реестр + выбранный), useChat (лента сессии)
components/     TerminalHeader, ChatWindow, ChatMessage, SourceSpoiler,
                ThinkingBubble, ChatComposer, CharacterSelector, CharacterAvatar, EmptyTerminal
```

* **Слой API** — `TerminalApi` знает только два вызова (`listCharacters`, `sendMessage`) и
  собирает URL'ы; компоненты про `fetch`, HTTP-коды и `AbortController` не знают. Сбои транспорта
  приводятся к `ApiError` и к фразе, которую можно показать оператору (`api/errors.js`).
* **Состояние** — в двух композаблах. `useCharacters` грузит реестр на `onMounted` и держит первого
  выжившего выбранным; `useChat` отвечает за ленту: реплика оператора добавляется сразу, ответ
  персонажа — по факту ответа, а сбой становится видимой строкой «Сбой канала», а не тихим отказом.
* **Компоненты** — по одной ответственности: `ChatMessage` рисует одно сообщение, `SourceSpoiler`
  сворачивает один чанк лора, `ChatComposer` владеет только вводом. Единственное место, где
  проверяется «можно ли отправить», — `App.vue`, потому что именно он владеет черновиком.

### Что видно на экране

* Вопросы оператора выравниваются по правому краю, ответы выживших — по левому, с аватаром-монограммой
  и именем; активный персонаж подписан в доке (`Responding agent`, `Ответит: …`).
* Пока идёт ответ, в ленте висит `Thinking`, а поле ввода блокируется и меняет placeholder.
* Источники из RAG печатаются под ответом сворачиваемыми спойлерами: **уровень достоверности**
  (официальный лор, граффити на стене, речь персонажа) со своей иконкой и цветом, происхождение
  записи (`No Mercy › The Subway`), `#id`, косинусное совпадение в процентах и полоска рядом.
  Уровни переводятся в подписи в `lib/lore.js` — граффити намеренно выглядит иначе, чем
  проверенный лор, чтобы слух не читался как факт.
* Селектор выжившего — выпадающий список вверх от кнопки (данные из `GET /api/v1/characters`);
  закрывается по Esc и по клику вне. Смена персонажа не влияет на уже полученные ответы, но
  следующее сообщение уходит с новым `character_id`.
* `Новая сессия` очищает ленту (история живёт в памяти вкладки), `API` ведёт в Swagger,
  статус в шапке отражает доступность реестра и даёт `Переподключиться` при обрыве.

Схема персонажа не содержит `avatar_url` — иконки на бэкенде не хранятся. `CharacterAvatar`
использует картинку, если API когда-нибудь начнёт её присылать, а сейчас рисует монограмму с
постоянным цветом на имя (`lib/personas.js`).

## Как работает RAG-пайплайн

`RAGService.process_chat_message(character_id, user_message)`:

1. **Персона** — `CharacterRepository.get_by_id()`; если персонажа нет, сразу
   `CharacterNotFoundError` → `404`, без обращения к провайдеру.
2. **Эмбеддинг вопроса** — `OpenAIClient.get_embedding(user_message)` → вектор на 1536 чисел.
3. **Раздельный поиск по трём уровням.** Вместо одного запроса делаются три независимых, у каждого
   свой бюджет и свой порог сходства (`RetrievalPolicy`):
   * `official` — проверенный лор, `4` записи, порог `0.25`;
   * `graffiti` — надписи со стен, `3` записи, порог `0.25`;
   * `voice` — реплики **самого отвечающего** персонажа (`character_name = character.name`),
     `2` записи, порога нет.

   Это и есть двухуровневость: слухи не конкурируют с фактами за одни и те же слоты контекста,
   поэтому стена граффити не может вытеснить проверенную запись — и наоборот.
4. **Векторный поиск** — `LoreChunkRepository.search_similar_chunks(...)` выполняет в SQL
   `embedding <=> :query` (косинусное расстояние), сортирует по возрастанию расстояния и возвращает
   `similarity = 1 - distance`; индекс HNSW ускоряет поиск, а фильтры `source_type` и
   `character_name` отсекают чужие уровни ещё в базе.
5. **Порог сходства — свой у каждого уровня.** Для доказательств слабое совпадение это шум, поэтому
   порог отсекает всё ниже `0.25` (эмбеддинги `text-embedding-3-small` на несовместимых текстах
   редко поднимаются выше `0.2`). Для реплик персонажа порога нет: это образец речи, уже суженный
   до одного говорящего, и две самые близкие его реплики полезны, даже если вопрос не про то, для
   чего они были записаны.
6. **Сборка брифинга** — `ArchivePromptBuilder` рендерит найденное тремя блоками с разными
   инструкциями: `<official_lore>` (только отсюда можно утверждать факт), `<wall_graffiti>`
   (чужой слух, пересказывать вслух как надпись на стене и относиться сообразно характеру) и
   `<speech_samples>` (копировать манеру речи, но не пересказывать реплики как события). Пустой
   уровень отмечается явно, чтобы модель видела: сведений нет, а не «забыли передать».
7. **Генерация** — системный промпт персоны + инструкция о языке из настроек + брифинг +
   few-shot примеры из `characters.few_shot_examples`. Ответ упаковывается в `ChatResponse` вместе
   с источниками всех трёх уровней.

Роли уровня и характера разведены намеренно: **что можно утверждать** решает пайплайн, а **как это
звучит** решает персона. Ник и Эллис получают одни и те же записи, но первый называет надпись
«чужой графоманией», а второй пересказывает её как свежую новость и вспоминает Кита.

## Корпус и ингестинг

Источник лора — [Left 4 Dead Fandom Wiki](https://left4dead.fandom.com). `app/ingestion/` — это
адаптер к вики: он скачивает разметку, разбирает её в плоские размеченные записи и складывает
снимок в `data/corpus/lore.jsonl`. Снимок лежит в git, поэтому `seed.py` воспроизводим, ревьюится
в диффе и работает без сети.

### Что берём

| Раздел | Страницы | Уровень | Записей |
|---|---|---|---|
| Происхождение заражения | `Green Flu`, `Carriers`, `CEDA`, `Military`, `Media Coverage` | `official` | 181 |
| Выжившие | биографии восьмерых + обзорная `Survivors` | `official` | 233 |
| Заражённые | общие, необычные, особые, `The Tank`, `The Witch`, `Boomer`, `Hunter`, `Smoker`, `Charger`, `Spitter`, `Jockey` | `official` | 780 |
| Кампании | `Campaigns` и пятнадцать кампаний L4D1/L4D2 | `official` | 223 |
| Убежища | `Safe room` | `official` | 38 |
| **Safe Room Inscriptions** | `Graffiti` — все надписи, сгруппированные по кампании и главе | `graffiti` | 396 |
| Реплики | `Bill/Quotes and Captions`, `Zoey/…`, `Francis/…`, `Louis/…`, `Coach/Quotes`, `Nick/Quotes`, `Rochelle/Quotes`, `Ellis/Quotes` | `voice` | 526 |

Всего — **2377 записей** с 50 страниц. Реестр источников — `app/ingestion/sources.py`: добавить
страницу значит добавить одну строку с темой и парсером.

### Как разбираем

* **`wikitext.py`** чистит MediaWiki-разметку: сноски, галереи, атрибуты, ссылки, таблицы. Две
  вещи сохранены осознанно. **Инфобоксы** (`{{Infobox infected|Health = 4000 …}}`) превращаются в
  строки `Health — 4000 (Normal & Survival)`: характеристики заражённых — самый спрашиваемый факт
  в архиве, и выбрасывать шаблоны целиком означало бы выбрасывать ровно их. **Таблицы** не
  удаляются, а выравниваются в строки, по той же причине.
* **`GraffitiParser`** делает одну запись на ветку разговора: стены убежищ содержат перепалки
  («NO ZOMBIE IS SAFE FROM CHICAGO TED» → «No it doesn't» → «2 1/2 HOURS»), и ответ бессмысленен
  без надписи, на которую он отвечает, поэтому вложенные пункты склеиваются со своей основой
  стрелкой `↳`. Заголовок записи — `кампания › глава`.
* **`ArticleParser`** режет статью по заголовкам и абзацам (потолок ~900 символов, чтобы в промпт
  влезало несколько записей). Лид статьи сохраняется всегда: это её собственное резюме. Заголовок
  записи — путь до раздела (`The Tank › Mechanics › Attacks`).
* **`QuotesParser`** собирает голосовой профиль характера из дампов реплик: группирует строки по
  ситуациям, отбрасывает односложные реакции («Ugh!»), ремарки в скобках и служебные пометки
  «(2 versions)», и ограничивает профиль 400 строками на персонажа. Дампы содержат тысячи строк,
  большинство из которых ничего не говорят о характере; в архив идёт то, что составляет манеру речи.

### Команды

```bash
make corpus-refresh    # перечитать вики и пересобрать снимок (без базы)
make reingest          # очистить lore_chunks и залить снимок заново
make seed              # схема + персоны + инкрементальный ингестинг снимка
python seed.py --refresh --corpus-only            # то же, что corpus-refresh
python seed.py --refresh --corpus-only --translate # + нормализация языка корпуса
```

Разметка кэшируется в `data/wiki_cache/` (в git не попадает), поэтому разбор можно повторять без
сети, а `--refresh` принудительно перечитывает страницы.

### Про перевод корпуса

Вики на английском, а терминал отвечает по-русски, поэтому в пайплайне есть опциональный этап
`translation.py`, нормализующий корпус в `CORPUS_LANGUAGE`. Замер на этом же корпусе: русский
вопрос про Зелёный грипп давал `0.53` против английской записи и `0.74` против её русского
перевода, при заметно большем отрыве от следующего кандидата. Но перевод — это дорогой проход:
на настроенном провайдере 16 коротких строк заняли ~21 с, а один длинный абзац статьи — ~47 с и
вернулся непереведённым. По всему корпусу это десятки минут, поэтому этап **выключен по умолчанию**
и включается флагом `--translate`. В любом случае поиск ранжирует правильную запись первым и на
английском: кросс-язычный поиск слабее, но работает, а `--translate` доступен тем, кому нужны
плотнее сходства. Непереведённый текст сохраняется как есть — частичный проход ухудшает корпус,
но не портит его.

## Тесты

```bash
pytest                                     # всё: юнит-тесты + интеграционные, если поднят PostgreSQL
pytest tests/test_rag_service.py           # только бизнес-логика, без БД и сети
pytest tests/test_ingestion_parsers.py     # разбор вики-разметки на встроенных примерах
```

**Юнит-тесты** не обращаются ни к PostgreSQL, ни к сети, ни к вики: `tests/fakes.py` содержит
in-memory реализации портов и детерминированный AI-клиент, `tests/test_ingestion_parsers.py`
работает на встроенной вики-разметке, а в `tests/test_api.py` через `dependency_overrides`
подменяются только внешние адаптеры — реальные роутеры, DI-граф и `RAGService` при этом работают
по-настоящему. Это и есть проверка того, что инверсия зависимостей сделана корректно.

**Интеграционные тесты** (`tests/test_integration_postgres.py`) поднимают всё по-настоящему: свой
PostgreSQL-инстанс, реальные репозитории, косинусный поиск через pgvector и HNSW-индекс, а также
проверяют, что надпись со стены не попадает в блок фактов. OpenAI подменяется локальным
HTTP-заглушкой (`tests/provider_server.py`), поэтому ключ и интернет не нужны. Тест сам создаёт
базу `<имя_базы>_test`, а если PostgreSQL недоступен — скипается, оставляя прогон зелёным:

```bash
docker compose up -d
pytest tests/test_integration_postgres.py
```

## Замечания по реализации

* `Base` — это `class Base(DeclarativeBase)`, а не `declarative_base()`: в SQLAlchemy 2.0 это
  каноничная форма, дающая нормальную типизацию `Mapped[...]` в подклассах.
* Сессии открываются на один HTTP-запрос (`Database.session` коммитит при успехе и откатывает при
  исключении), `expire_on_commit=False` позволяет безопасно отдавать ORM-объекты в `response_model`
  уже после закрытия сессии.
* Размерность вектора берётся из настроек (`EMBEDDING_DIMENSIONS`), а не хардкодится в модели,
  но должна совпадать с размерностью выбранной модели эмбеддингов.
* Комментарии в коде только там, где решение неочевидно (например, почему `<=>` — это расстояние,
  а не сходство).
